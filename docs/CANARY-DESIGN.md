# 页面停住类问题的检查设计

## 一、要抓的是什么

Reddit 那次事故的形态：我们拦掉一个**应用会 await 的子资源**（`||redditstatic.com/shreddit/sentry-`，一个懒加载 JS 分块），请求被拦后 promise 既不 resolve 也不报错，页面在服务端渲染的内容显示完之后**不再前进**。评论区不从 DOM 里消失，而是从来没有出现。

这一类问题的共同特征：

- 页面**没有报错**，控制台干净；
- 元素**没有被隐藏**（`data-adblow-hidden` 为 0）；
- 症状是"**加载到一半就不动了**"，而关闭扩展就恢复；
- 根因是**网络规则**，不是隐藏逻辑，也不是主世界守卫。

因此检查的目标不是"页面看起来对不对"，而是"**页面有没有走到它自己该到的下一步**"。

## 二、两层设计

### A 层：规则体检（离线、每次 CI 都跑）

对一个**站点清单**，逐条检查编译后的规则集，列出"会拦掉这些站点自身脚本或 XHR 的规则"。

具体判定：

1. 规则的动作是 `block`，且 `resourceTypes` 含 `script`、`xmlhttprequest` 或 `sub_frame`（拦这些类型才可能让应用停住；拦图片、字体不会）；
2. 规则的匹配式指向清单里某个站点的**自有域名**（站点主域及其 CDN 子域，例如 `redditstatic.com`、`sinaimg.cn`）；
3. 输出：站点、规则 id、卷名、匹配式、类型、来源列表。

产出不是"失败/通过"，而是一张**可人工过目的表**。当前规模估计在 20 条以内——Reddit 那条、`/shreddit/perfMetrics`、`||reddit.com/timings/` 都会出现在表里。

价值的来源：这类规则**数量很少**，而每一条都可能让一个站点整页不可用。人看一眼就能判断"这条该不该拦"，比等用户报告快得多。

成本：零网络、毫秒级、不需要浏览器。可以直接进现有测试套件。

### B 层：金丝雀差分（联网、发布前或每日）

对每个金丝雀页面，用两套环境各加载一次：**装扩展**与**不装扩展**，比较"页面是否走到预期的那一步"。

判定不看截图，只看三个量：

| 量 | 采集方式 | 用途 |
|---|---|---|
| `signal`：预期元素是否出现、耗时多少 | DOM 查询轮询 | 主判据 |
| `blocked`：被拦请求的主机名与类型 | CDP `Network.loadingFailed` 的 `blockedReason` | 定位到规则 |
| `errors`：未捕获异常与未处理 rejection | CDP `Runtime.exceptionThrown` | 区分"我们拦坏了"与"站点自己坏" |

通过条件（同时满足）：

1. 装扩展时 `signal` **出现**；
2. `signal` 的出现时间不超过"不装扩展"基线的 **2 倍**；
3. `errors` 的数量不超过基线的 **+2**。

失败时输出的东西决定这个检查是否有用：**必须列出被拦的主机名与资源类型**，否则只会在红了的构建里再查一遍。

## 三、金丝雀清单

每个站点只验**一个**信号，宁少不多。

| 站点 | 类型 | 预期信号 |
|---|---|---|
| Reddit 帖子页（公开） | SSR + hydration | 评论区出现 `shreddit-comment` 至少 1 个 |
| 新浪财经个股页 | 传统页面 | 研报面板的标题节点可见 |
| 任意无登录的新闻正文页 | 静态为主 | 正文段落数 ≥ 基线的 90% |
| 一个视频站播放页 | 重 JS | 播放器容器可见，且 30 秒内出现播放进度更新 |

选择标准：**公开、无需登录、结构稳定、有明确的"后加载"信号**。凡是要登录、要过 cookie 墙、要过反爬挑战的，一律不进清单——那些失败无法归因，只会制造噪声。

清单本身是**契约**：站点改版会让信号失效，需要定期复核。建议每月看一眼，失效就换，而不是让检查长期变红。

## 四、稳定性处理

联网检查天然不稳定，所以：

- 每个页面**重试 2 次**，任一次通过即算通过；
- 连续两次运行都失败的金丝雀标记为 `unstable`，从门禁里摘出并开 issue，不阻塞发布；
- 每次运行把结果写成 JSON 存档，便于判断"是这次改动导致的，还是站点自己变了"。

## 五、明确不做

- **不做截图比对**：字体、广告位、A/B 实验都会让它变红，噪声远大于信号；
- **不做全站爬取**：成本高、易被封、失败难归因；
- **不检查"广告有没有被拦住"**：那是另一件事（验收套件已经在做），两者混在一起会让失败无法归因；
- **不用"页面看起来正常"作为判据**：必须是**一个具体的、后加载的 DOM 信号**。

## 六、落地顺序

1. **先做 A 层**。它离线、便宜、覆盖了这次的根因类别，而且产出的那张表本身就是可用的审查材料。
2. **再做 B 层**。先从 Reddit 一个金丝雀开始，跑通"装/不装扩展的差分"这套机制，再逐个加站点。
3. A 层进每次 CI；B 层进发布前的检查（或者每日定时，与自动发版同一个工作流）。

## 七、这次事故在两层里分别会怎样暴露

- **A 层**：`||redditstatic.com/shreddit/sentry-` 会被列出——`block` + `script` + 指向 `redditstatic.com`，正好命中全部三条判定。审查时能看出"这条会拦 Reddit 自己的脚本"。
- **B 层**：装扩展时 `shreddit-comment` 始终为 0，不装扩展时 30 个——信号缺失 + 被拦清单里出现 `redditstatic.com`，能在一分钟内定位。
