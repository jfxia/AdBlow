# 与主流产品的差距，以及下一步计划

本文的自我数据来自本仓库当前构建产物，竞品能力按各自公开文档与实测印象整理。凡是推断或不确定
的地方都写明了，方便以后校正。

## 一、先说结论

AdBlow 与主流产品的差距不在"功能数量"，而在三件事：

1. **规则更新要等发版**。uBlock Origin 与 AdGuard 都能在运行时更新列表；AdBlow 把列表编译进静态
   规则集，MV3 没有远程替换静态规则集的接口，所以刷新一次列表等于发一个版本。定时自动发版只把
   周期从"人工决定"变成"每周一次"，没有消除结构性延迟。
2. **过滤表达能力有缺口**。过程式隐藏规则 `#?#`、HTML 过滤 `##^` 未实现，通用（非域名限定）隐藏
   规则也没有注入；脚本注入 13 个规范名，未覆盖的仍有 385 条。
3. **用户可控性不足**。uBlock 的元素选取器、动态过滤面板、日志器是"出问题时用户自己能修"的
   工具；AdBlow 只有自学习规则的查看与删除，没有手动添加规则的入口。

与 uBlock Origin 经典版、AdGuard 桌面版相比，AdBlow 落后一个量级。不过这两者不受 MV3 约束，
比较意义有限。真正同赛道的是 uBlock Origin Lite 一类的 MV3 产品：它们同样受静态规则集与配额
约束，比拼的是规则组织、动态规则热更和界面。

两个数字值得单独盯住：

- **规则预算已用 97%**。这不是"还有余量"的意思，是"再加一批规则就需要先腾地方"。下一步要么提高

- **1 万条外观选择器没打进去**。这是纯覆盖损失，不涉及算法。

## 三、逐维度对比

| 维度 | AdBlow | uBO Lite（MV3 同类） | uBO 经典 / AdGuard |
|---|---|---|---|
| 请求拦截 | 静态规则集 6 卷，23,278 条 | 多份静态规则集，按需启用 | 自研引擎，无配额压力 |
| 规则热更新 | **需发版** | 动态规则热更 | 运行时更新 |
| 过程式隐藏 `#?#` | 未实现 | 部分支持 | 支持 |
| HTML 过滤 `##^` | 未实现 | 不支持 | 支持 |
| 通用隐藏规则 | 未注入（只注入域名限定） | 支持 | 支持 |
| 脚本注入 | 13 个名字 / 2,286 条 | 有限 | 上百个名字 |
| 元素选取器（手动加规则） | **无** | 有 | 有 |
| 动态过滤 / 按站点细粒度开关 | 只有整站开关 | 有 | 有 |
| 反过滤墙 | 检测 + **用户确认后**处理 | 部分自动 | 自动 |
| 行为判定 / 自学习 | **独有** | 无 | 无 |
| 性能基准 | 无公开数据 | 无 | 有 |
| 界面语言 | 5 种 | 数十种 | 数十种 |

差距最大的一行是"元素选取器"。它不只是功能，更是**误伤的自助出口**：站点被误判时，用户能当场
加一条例外；没有它，用户只能等版本更新或整站关闭。

## 四、计划

### 阶段一：把规则规模的天花板推开（下一个版本）

1. **不再提高规则预算**（实测结论，推翻原判断）
   - 预算从 24,000 提到 29,500 后，编译输出**一条没变**：`budgetUsed` 仍是 21,118、
     `budgetTruncated` 仍是 0。没有候选因空间不足被丢弃，所以预算买不到任何覆盖。
   - 真正的损失在两处：解析阶段 **4,514 条规则用了编译器不支持的选项**（`unsupported-option`），
     以及外观选择器 **35,853 条可用、实装 25,467 条**。
   - 因此本阶段的第一项改为：**统计不支持的选项分布**，按出现频次补实现（每补一个选项，
     都是一批规则直接可用）。
2. **补齐外观选择器**：把未纳入的 1 万条按分片体积重新分配后打进去，或明确记录被放弃的原因。
3. **cookie 提示处理收尾**：功能已实现，需要在真实站点上校准阈值与误伤。

### 阶段二：解决结构性问题（一到两个月）

4. **动态规则热更通道**（价值最高）。列表更新改为下发给 `declarativeNetRequest` 的动态规则，
   不再等商店审核。需要：托管端点、规则签名、版本锚点、拉取失败时回退到内置规则集，以及
   "只下数据不下代码"的边界约束（脚本注入必须随包）。
5. **元素选取器**：右键拾取页面元素、生成一条仅本站生效的隐藏规则，可在规则管理页撤销。
   这是把"误伤"从开发者问题变成用户可自助的问题。
6. **过程式过滤 `#?#`**：需要一个新的外观规则运行时（CSS 之外的选择器求值），成本中等。

### 阶段三：补覆盖率与工程债（季度级）

7. 脚本注入扩充：从 385 条未覆盖里挑出现频率最高的一批，逐个带测试上线。
8. **性能基准**：内容脚本每页耗时（P50/P95）、判定阶段占比、快照捕获成本。目前完全没有数据，
   这是发布前最该量化的一项。
9. 语言扩充（de / ru / pt-BR / ko）与 Chrome Web Store 上架。

## 五、明确不做

- 不设付费白名单，也不接受付费放行；
- 不绕过登录墙、付费墙与年龄验证，那不属于广告拦截；
- 反过滤墙维持"用户逐站确认"，不改成自动处理。误判的代价高于漏判，这条不改。

## 六、风险

- **规则规模是最硬的约束**。阶段一若测出可用额度远低于 30,000，后面几项都要重新排期。
- **热更通道引入服务端**，会打破"全部本地处理"的现状，需要在隐私说明里写清楚：只拉规则数据，
  不上报任何浏览信息。
- 竞品数据按公开文档整理，可能滞后；对比结论以"能力有无"为主，不以具体数字比较。
