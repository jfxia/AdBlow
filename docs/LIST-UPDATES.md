# 过滤列表的更新策略

本文回答一个问题：AdBlow 打包时引用了 EasyList 这些开源数据，以后它们更新了怎么办。

## 先说结论

- **MV3 的静态规则集是打包文件，没有远程替换的接口。** 所以刷新列表 = 发一个新版本、
  过一次商店审核。这一点没有绕过去的办法。
- 能远程改的只有**动态规则**（`updateDynamicRules`）。把它用起来可以做到"不发版也更新
  一部分规则"，但有几条不能碰的边界（见下文路线 B）。
- 现在的做法：`pnpm update-lists` 一条命令完成刷新与打包；产物里带上了列表日期，规则管理页
  也会显示，用户和维护者都能一眼看出手上这份规则是哪天的。

## 为什么静态规则集不能远程更新

静态规则集写在 manifest 的 `declarative_net_request.rule_resources` 里，随扩展一起分发。
`getEnabledRulesets()` 和 `updateEnabledRulesets()` 只能**开关**已经打包进去的那几卷，
不能替换它们的内容。浏览器这么做是为了防止扩展在用户不知情时改变拦截行为。

能远程下发的只有动态规则与会话规则。这里有个版本分界：**Chrome 120 起**，动态规则与会话
规则的上限从"一个合并常量"改成了两个独立常量。本项目的 `minimum_chrome_version` 正好是
120，所以可以直接按新规则设计。

## 实测配额（在 Edge 155 里读的实际返回值）

| 常量 | 值 | 对我们的意义 |
|---|---|---|
| `MAX_NUMBER_OF_DYNAMIC_RULES` | 30,000 | 我们编译出 23,515 条（21,146 拦截 + 2,369 例外），**装得下**，但吃掉 78% 配额 |
| `MAX_NUMBER_OF_UNSAFE_DYNAMIC_RULES` | 5,000 | 正则 / 跳转 / 改头这类"不安全"规则的上限。我们只有 33 条正则，余量充足 |
| `MAX_NUMBER_OF_SESSION_RULES` | 5,000 | 会话规则，重启即失效，适合临时放宽 |
| `GUARANTEED_MINIMUM_STATIC_RULES` | 30,000 | 官方保证的静态额度 |
| `getAvailableStaticRuleCount()` | 308,871 | 干净环境下的共享池余量 |

> ⚠️ **那个 308,871 不能用来做预算。** 它是"这台机器、只装了我们一个拦截扩展"时的余量。
> 官方只保证 30,000，多出来的部分来自全局共享池，用户装了别的拦截扩展就会互相挤占，
> 而且**被挤掉的是哪几条无法控制**。本项目的编译预算定在 24,000（留 20% 余量）是故意的，
> 不要因为看到 30 万就把预算提到十万级。

## 三条路线

### 路线 A：定期发版（现状，建议先把它做扎实）

```bash
pnpm update-lists      # 抓取 → 编译 → 构建 → 测试 → 打包，并打印刷新前后的列表日期
```

然后改 `package.json` 的版本号，再 `pnpm package` 一次，把 `release/adblow-<版本>-edge.zip`
传到 Edge 加载项后台。

- **节奏建议**：每月一次，遇到明显误杀或漏拦就随版本一起发。EasyList 一天会更新数次，
  但编译到我们这份子集之后变化有限，不必追每日。
- **审核通过后**，已安装的用户会在数小时内自动更新，不需要他们做任何事。
- 代价：审核要等；没更新的用户会一直用旧列表。这也是为什么界面上要显示列表日期 ——
  用户报问题时，第一件事就是确认他手上的规则是不是过期了。

### 路线 B：运行时增量更新（可行，但边界必须守住）

做法是：把**编译产物**放到自己的站点或 GitHub Releases，扩展每隔一段时间取一份小清单，
把新增规则装成动态规则；元素隐藏数据本来就由内容脚本向后台取用，可以直接存进
`storage.local`。

能做到"不发版也更新"，但下面六条不能破：

1. **只下数据，不下代码。** `##+js(...)` 脚本注入属于可执行代码，远程下发会踩商店
   "禁止远程代码"的红线。12 个脚本注入规则与数据表必须永远随包。
2. **下载域名要写进 `host_permissions`**，并在商店说明与隐私声明里讲清楚只下载规则数据、
   不采集任何信息。
3. **给增量设预算上限。** 动态规则总共 30,000 条，其中"不安全"类只有 5,000 条。
   目前我们只用了 33 条正则，空间够，但增量必须限个顶（例如最多 5,000 条），
   不能让它慢慢顶满。
4. **分批安装。** 一次 `updateDynamicRules` 塞几万条容易被 service worker 回收打断，
   要分块、记进度、能续传。
5. **取不到就回落包内基线。** 断网或对端挂了，不能变成"完全没规则"。
6. **给用户开关**：自动更新规则数据（每日 / 每周 / 关闭），默认开，但只下载、不上传。

### 路线 C：混合（推荐）

包内基线照旧（离线可用、开箱即用、脚本注入永远随包），在此之上加一条可选的增量通道，
只用来更新网络规则与元素隐藏数据。这是 AdGuard 一类产品的做法，兼顾"装上就能用"和
"规则够新"。

## 现在已经落地的部分

- `pnpm update-lists`：抓取 → 编译 → 构建 → 测试 → 打包，并打印刷新前后的列表日期与条数。
  版本号不自动改：商店按版本区分，应当由人决定这是补丁还是小版本。
- 产物里多了 `list-info.json`（列表 id、抓取时间、网络规则与例外条数、脚本注入域名数）。
- 规则管理页显示一行：**内置过滤列表数据：抓取于 2026-10-12，共 6 份列表、21146 条网络规则**。
  用户报问题时可以直接把这一行发过来。

## 许可提醒

- 不论随包分发还是远程分发，都要保留 EasyList 与 uBlock Origin assets 的署名与许可
  （见 README 的致谢一节）。
- 走远程分发时，最好同时提供编译产物与生成脚本的获取途径 —— GPL 系许可要求能拿到对应源码。
